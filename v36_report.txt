## 1. v3.6 设计思路（核心：节奏控制层）

v3.5 实现了转场治理（生成层去转场词 + 剪辑层语义匹配 + 真实 xfade + P1-P4 自检）。
v3.6 在 v3.5 之上补全节奏层，让**外部节奏**（剪辑）匹配**内部节奏**（动作/鼓点）：

1. **拍点对齐**：每段时长 = 拍点整数倍；切点 = downbeat 边界
2. **快慢慢呼吸**：phase = {slow_open, fast_middle, slow_tail}
3. **变速是节奏王牌**：fast_middle 段中段 50% 窗口 ×1.35 快放，前后各 25% 慢入/慢出
4. **fancy 转场去重**：沿用 v35 ≤ 2 预算 + 类型全局去重

## 2. Step 1：rhythm_planner_v36.py（节奏规划）

**输入**：`storyboard_v35.json` + `beats.json`（120 BPM 理论拍点）+ `transition_plan_v35.json`
**输出**：`output/pipeline_v36/sb/rhythm_plan_v36.json`

**核心函数** `plan_rhythm(shots, beats, downbeats, beat_period)`：

- `assign_phases(n_shots)`：把 n 段切成三段式 → `[slow, fast...fast, slow]`
  - n=6 → `[slow, fast×4, slow]`（v36 默认）
  - n=3/4/5：自动调整头尾 slow 数
- 每段时长：snap 到整数拍（v35 10s = 20 拍，不重新切分）
- 每个 shot 输出：
  - `start_beat` / `duration_beats` / `duration_sec`
  - `phase`（slow_open / fast_middle / slow_tail）
  - `speed_factor_default`
  - `speed_window.windows`：变速窗口列表
    - slow_open/tail：空 windows（factor=1.0）
    - fast_middle：3 个窗口（前 25% hold / 中 50% ×1.35 / 后 25% hold）
- `cut_points`：每段边界 at_sec（必对齐到拍点网格）
- `transition_plan_cross_check`：与 v35 transition_plan 的 at_sec 交叉校验

**关键技术细节**：
- `BPM = 120.0`，`BEAT_PERIOD = 0.5s`，`BAR_PERIOD = 2.0s`
- 切点对齐容差 `CUT_ALIGN_TOLERANCE = 0.05s`（per 任务书 V1）
- 时长对齐容差 `DURATION_ALIGN_TOLERANCE = 0.1s`（per V2）
- slow 段最小拍数 `SLOW_MIN_BEATS = 6`（= 3s）
- fast 段速度因子 `SPEED_FACTOR_FAST_MIDDLE = 1.35`
- **确定性**：相同 SHOTS 跑 N 次结果一致（无 random）

**Dry-run 验证**：

## 3. Step 2：speed_segment_v36.py（局部变速）

**输入**：`rhythm_plan_v36.json` + `clips/`（6 段 10s mp4）
**输出**：`clips_sped/shot{01-06}.mp4`（按 rhythm_plan 应用变速）+ `speed_v36_meta.json`

**核心技术**：ffmpeg **filter_complex** 多窗口 trim + setpts + concat
（v34 的单 `-vf setpts=...*enable=` 语法不正确，v36 重写为正确的多窗口滤镜链）

**关键 ffmpeg 片段**（fast_middle 段）：
```bash
ffmpeg -y -i shot02.mp4 -filter_complex '
[0:v]split=3[sv0][sv1][sv2];
[sv0]trim=0.000:2.500,setpts=PTS-STARTPTS[sv0_out];
[sv1]trim=2.500:7.500,setpts=(PTS-STARTPTS)/1.3500[sv1_out];
[sv2]trim=7.500:10.000,setpts=PTS-STARTPTS[sv2_out];
[sv0_out][sv1_out][sv2_out]concat=n=3:v=1:a=0[vout]
' -map [vout] -an -c:v libx264 -crf 20 ...
```

**关键细节**：
- `setpts=(PTS-STARTPTS)/factor` —— 加速 factor 倍（不是 ×，是 /）
  - ×1.35 会慢放 1.35×；÷1.35 才是快放 1.35×
- 慢入/中段/慢出 三窗口分别 trim → setpts → concat
- 无音频（`-an`），由 compose_final_v36 铺 BGM

**实测时长**：
| shot | phase | strategy | 输入(s) | 输出(s) | 期望(s) |
|------|-------|----------|---------|---------|---------|
| 01 | slow_open | hold | 10.125 | 10.125 | 10.125 ✓ |
| 02 | fast_middle | slow_in_fast_slow_out | 10.125 | 8.750 | 8.704 ✓ |
| 03 | fast_middle | slow_in_fast_slow_out | 10.125 | 8.750 | 8.704 ✓ |
| 04 | fast_middle | slow_in_fast_slow_out | 10.125 | 8.750 | 8.704 ✓ |
| 05 | fast_middle | slow_in_fast_slow_out | 10.125 | 8.750 | 8.704 ✓ |
| 06 | slow_tail | hold | 10.125 | 10.125 | 10.125 ✓ |

**理论 vs 实际 8.75 vs 8.704 = 0.046s 误差**：因 frame rounding（24fps × 0.5s = 12 frames；trim 时按 keyframe 对齐有微小误差）

## 4. Step 3：compose_final_v36.py（xfade + 节奏 + fancy 去重）

**输入**：`clips_sped/` + `transition_plan_v35.json` + `rhythm_plan_v36.json` + `bgm_v32.wav`
**输出**：`final_v36_60s.mp4` + `_meta.json`

**vs compose_final_v35 关键差异**：

1. **fancy 去重 + 预算**：
   - `dedupe_fancy_transitions`：每个 fancy 类型（fadeblack/fade）全局仅首次出现
   - `enforce_fancy_budget`：fancy 总数 ≤ `FANCY_BUDGET_MAX=2`
2. **音频探测**：sped clips 经 speed_segment 去音频 → 探测到无音频 → 直接走 BGM-only 路径（不再 acrossfade 输入音频）
3. **xfade offset 累积**：保留 v35 的 offset 累积逻辑
4. **拍点对齐**：xfade offset 与 `rhythm_plan.cut_points.at_sec` 对齐

**xfade 链**（v35 transition_plan → dedupe+budget → xfade）：
- shot1→shot2: hard_cut (0.001s)
- shot2→shot3: hard_cut (0.001s)
- shot3→shot4: hard_cut (0.001s)
- shot4→shot5: dissolve (0.3s)
- shot5→shot6: dissolve (0.4s)

**总输出时长计算**：
- 输入：10.125 + 4×8.75 + 10.125 = 55.25s
- xfade 扣减：0.001 + 0.001 + 0.001 + 0.3 + 0.4 = 0.703s
- 输出：54.547s（与 ffprobe 实测 54.6s 一致）

**注意：54.6s vs 60s 偏差是设计行为**——fast_middle 段 ×1.35 压缩导致总时长比 60s storyboard 短 5.45s。这是节奏设计意图（PV 节奏王牌：动作密集快放），不是 bug。
