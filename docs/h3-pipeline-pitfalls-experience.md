# AI 视频管线 · 踩坑经验与工程规范（v36 → v365 沉淀）

> 适用范围：MiniMax H3 动漫 PV 生成管线的开发与迭代（ai-video-pipeline）
> 版本时间：2026-08-20，由 v36→v361→v362→v363→v364→v365 六轮实战教训总结
> 目的：以后开发相同流程时避免重复踩坑，直接复用已验证的正确做法

====================================================================
## 0. 铁律速览（TL;DR）
====================================================================
1. ffmpeg xfade 有**边界 bug**：offset+duration 恰好=第一路流时长时不产出后续段
   → 硬切用 concat demuxer；dissolve 用 xfade 且 offset 留 0.06s MARGIN
2. **验证绝不信 format.duration**（会被音频流时长骗）→ 必须读 video stream 时长+帧数
3. 拼接 scale/RES **必须与源比例一致**（竖屏源就别 scale 成横屏）
4. H3 生成 clip **首 0.5s 常带白淡入** → prompt 禁 fade-in + 生成后 trim 掉 + 首帧 YAVG 检查
5. 花哨转场（色彩爆炸/布料扫镜）是**生成层**：写进 H3 prompt，不是后期 xfade；想有必须重投
6. **全流程重构必盘点旧版已验证的成果**（词库/prompt 结构/模块），防丢失
7. 视觉评审走 `vlm_config.py` zen HTTP 通道（opencode read 工具会误报不支持图像）
8. VLM 429 配额会挂 → 需 ffmpeg 定量兜底（YAVG/帧数/分辨率）
9. 工程上别每版本复制脚本 → 借鉴 stop_at 分阶段 checkpoint + 状态机 + preflight 校验
10. Windows 中文 prompt 用 UTF-8；远程 PowerShell 里 `$_` 会被本地 bash 吞掉

## 1. ffmpeg xfade 边界 bug（最致命，三版连环栽）
====================================================================

### 现象
v36/v361/v362 三版成片全部失败：
- v36：video 截断到 shot01（245 帧 / 10.2s）
- v361：整片翻倍 109.5s（offset 累加 + tpad 错误）
- v362：又截断 245 帧

### 根因（opencode 定位 + 实测确认）
**ffmpeg xfade 原生 bug**：
> 当 `offset + xfade_duration` 恰好等于**第一路输入的实际流时长**（exact boundary）时，
> ffmpeg 不产出后续段（或只输出第一路）。

例：shot01 时长 10.125s，第一处 xfade offset=10.124, duration=0.001
→ offset+duration = 10.125 = 恰好边界 → 截断。

**注意**：offset 数值算对了也没用，只要撞上边界就触发。v362 的 offset 完全正确
（迭代式算死 [10.124,18.873,...]）依然截断。

### 正确解法（v363 已验证）
- **硬切段间 → `ffmpeg concat demuxer`**（v3.4/v3.5 已验证稳定，零 xfade 边界问题）
- **dissolve 段间 → xfade，但 offset 严格留安全边距**：
  ```
  offset = input1_dur - xfade_d - SAFE_GAP   # SAFE_GAP = 0.06s
  assert offset + xfade_d < input1_dur - 0.05   # 硬断言，绝不撞边界
  ```
- v363 用 2 处 xfade + concat，成片 54.42s/1306 帧 stream-level 全 PASS

### 教训
- 组间用 xfade（少边界点），组内用 concat（零边界），是最稳的组合
- 每个 xfade 前必须 assert 不撞边界
- 链式 xfade 越少越好——每多一个边界点，风险高一档

## 2. 验证陷阱：format.duration 会骗人（opencode 也被骗）
====================================================================

### 现象
opencode 用 `ffprobe format.duration` = 54.6s 判断"视频正确"，实际 video 流只有 245 帧/10.2s 截断了。

### 根因
`format.duration` 是**容器级时长**，可能被**音频流时长**影响。v36 音频 54.6s（正常），
视频 10.2s（截断），format.duration 却显示 54.6s → 误判正确。

### 正确验证（必须含）
```bash
# 视频流真实数据（不信 format.duration）：
ffprobe -v error -select_streams v:0 \
  -show_entries stream=duration,nb_frames,width,height,pix_fmt -of default=noprint_wrappers=1 out.mp4
# 断言：
#   video duration ≈ 目标时长
#   nb_frames ≈ duration × fps
#   width×height = 预期分辨率（如 768x1344）
#   pix_fmt = yuv420p
```
audio 也要单独 -select_streams a:0 查，且与 video 时长对齐。

### 教训
- 验证脚本必须区分 video/audio stream，不能只信容器 format
- nb_frames 是最硬的自检信号（截断/翻倍都会在帧数上露馅）

## 3. 拼接比例压扁（v363 横屏 bug）
====================================================================

### 现象
v363 输出 1344x768 横屏，但 H3 源是 768x1344 竖屏 → 所有素材被压扁。
用户一眼看出"比例被压缩了"。

### 根因
拼接脚本 scale/RES 写死成 1344x768（横屏），没跟着源走。

### 正确解法
- 输出的 width×height 必须与源一致（竖屏源 → 768x1344）
- 若需适配，用 `force_original_aspect_ratio=decrease,pad=...` 垫边，禁直接拉伸
- verify 里加 resolution 断言（v364 已加）

### 教训
- 涉及 Scale/Resize/RES 常量，验证必须含分辨率断言，防回退
- 用户偏好竖屏 9:16 时，从生成到拼接全链路保持竖屏

## 4. H3 生成 clip 的白淡入（dissolve 处"白帧"）
====================================================================

### 现象
v363 的 dissolve1_post/dissolve2_post 被 VLM 判为"白帧"，整体评分被拖累。用户反馈"41 秒画面人物距离不一"。

### 根因（归因分析）
**shot05/shot06 源内容首 ~0.5s 从白淡入**（H3 生成器特性），不是 dissolve filter bug。
v363 报告实测：frame0 YAVG=232.6（近全白）→ frame1 208 → 逐渐正常。

### 正确解法（v364 已验证）
1. **prompt 显式声明**："no fade-in from white, no fade-in from black, first frame must have content"
2. **生成后 trim 掉每段开头 0.5s 白淡入**（v364 用 concat demuxer + 单独 trim pass）
   - v364 实测：shot01 从 10.125s → 9.625s，首帧 YAVG 221→153.6（白淡入消失）
3. **首帧 YAVG 检查**：首帧必须非白（YAVG<220）非黑（YAVG>20），异常重投该段

### 教训
- 白淡入是生成层问题，trim 治标、prompt 治本、重投根治——三层都做
- trim 会改变总时长 → 所有后续 offset/总时长要重算

## 5. 生成层转场 vs 后期拼接层转场（v364 丢失特效）
====================================================================

### 现象
v364 重构后成片"没有转场特效了"（用户反馈）。只剩 dissolve+硬切。

### 根因
**花哨转场（色彩爆炸/布料扫镜/斜切划像/漫画分屏）是生成层**——写进 H3 prompt 让生成器渲染，
不是后期 ffmpeg xfade。v364 重构时把 v3.2 的 `TRANSITIONS_BLOCK` 词库整个丢了
（char_blocks_v364.json 里没有这个键），导致 prompt 无转场词 → H3 生成无特效。

### 正确做法（v365，正在执行）
- **转场词写进 H3 prompt 的 `[TRANSITION_RHYTHM]` 块**，生成层渲染，段开头 1-2s 有效果
- **每种转场全片只用一次**（用户明确要求，去重）
- 词库（v3.2 验证过）：
  - color explosion / ink burst sweeping across frame（色彩爆炸/墨爆）
  - fabric wipe（布料扫镜：衣摆/发丝扫过镜头）
  - diagonal slash wipe（斜切划像）
  - comic panel split-screen（漫画分屏）
  - whip pan with motion streaks（甩镜）
  - halftone dot overlay flash（半调网点闪光）
- 段内只放 1 个转场特效，不堆砌；开场段可不放（净开场定调）

### 教训
- **全流程重构必盘点旧版已验证的模块/词库/prompt 结构**，防丢失
- 生成层特效想要必须重投 H3，不可能后期硬加
- 转场是"生成层"还是"拼接层"要想清楚：花哨=生成，基础(dissolve/切)=拼接

## 6. 角色/规格版本间漂移
====================================================================

### 现象
v364 任务书 §3.2 角色色号跟 v363 相反（学姐=棕发/学妹=黑发，但 v363 是学姐=黑发/学妹=棕发）。

### 影响
v364 是全流程重构，6 段自洽即可，风险可控。但若只是部分重生成，会跟已有 clip 的角色不一致。

### 规范
- 角色锚点（发型/发色/装饰/服装）**跨版本要稳定**，重构时先确认，不随意改
- 要用一个权威定义源（如 char_blocks JSON），各段/各版本引用同一 source of truth
- 部分重生成时，prompt 必须引用同一角色锚点，防漂移

- 兜底结果如实标注"quantitative only"，不冒充 VLM 判断

## 8. 工程范式：别每版本复制脚本（借鉴 MPT）
====================================================================

### 现状问题
vi 系列是平铺脚本：compose_final_v36/v361/v362/v363/v364.py、verify_v3xx.py、
prompt_pack_v3xx.py……每版本复制改后缀，无统一架构，状态不透明。

### 借鉴 MoneyPrinterTurbo（MIT，11万 star）的成熟范式
1. **stop_at 分阶段 checkpoint**：
   管线可停在 script/audio/video 等任意节点返回中间产物 → 每阶段独立调用、断点续跑
2. **preflight 前置校验**：开始前校验所有前置条件（key/依赖/路径/长宽比），尽早失败
3. **统一状态机 + 进度**：sm.state.update_task(task_id, state, progress) 逐阶段推进
4. **多 provider 抽象 + 响应规范化**：不同模型通道统一封装，规范化返回
5. **日志脱敏**：_redact_secret 把 API key/密码打码，防泄露

### 建议落地（优先级排序）
- P1：统一任务编排 + 分阶段 checkpoint（解决"状态不透明、每版本复制脚本"）
- P2：preflight 校验 + 结构化状态/进度
- P3：多 VLM provider 抽象 + 响应规范化

## 9. 环境/编码坑
====================================================================

1. **Windows 中文 prompt 必须 UTF-8**：GBK 会乱码（cmd findstr 匹配中文失败）
2. **远程 PowerShell 里 `$_` 会被本地 bash 吞**：命令里 $_ 要转义，否则报
   lastWriteTime 无法识别之类的错
3. **路径无中文/空格**：Windows 一键包/部署要求干净路径
4. **H3 每段 10-12 分钟**（240 帧）：批量 6 段约 1 小时，poll 超时需设长（>600s）
   或用后台批量轮询，避免单段脚本超时被 kill
5. **ComfyUI 过夜会停**：视频/H3 任务前先查 8188 是否监听，重启用 schtasks /run comfy_h3

## 10. 推荐工作流（已验证）
====================================================================
1. 先定规格：分辨率（竖屏 768x1344）、帧率 24fps、时长、BGM 拍点
2. 定节奏：快慢呼吸（参考视频 scene 检测切点），切点落拍
3. 写 prompt：直接上角色 + 单动作链 + 无白淡入 + 转场特效（生成层，全片去重）
4. H3 生成：逐段，首帧 YAVG 检查，异常重投
5. 拼接：硬切 concat + dissolve xfade 留 0.06s MARGIN，竖屏 yuv420p
6. 验证：stream-level（video 时长/帧数/分辨率/pix_fmt）+ 采样 YAVG + 首帧非白
7. 评审：vlm_config.py zen HTTP + ffmpeg 定量兜底
8. 报告 + commit
